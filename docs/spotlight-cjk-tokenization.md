# Spotlight 中文文件名分词

Spotlight 对中日韩文件名的匹配不是简单的字符串子串查找。当汉字中夹着数字和连字符时，
索引端和查询端的分词可能不一致，导致输入完整文件名反而查不到。

## 可复现样例

使用专门生成的测试文件：

```text
~/Documents/starfind-fixture/项目示例-1-年度总结与数据复盘.md
```

在部分 macOS 版本上，较短的中文片段可以命中，而包含「数字 + 连字符 + 中文」边界的整串可能失败。
`kMDItemFSName ==` 也不能绕过这个问题，因为 Spotlight 仍会使用自己的词法规则。

## StarFind 的处理

StarFind 使用两级查询：

1. 先使用正常的 `LIKE[cd] "*query*"` 查询。
2. 如果查询完成且结果为空，将中日韩字符拆分为 AND 条件重查。
3. 对候选结果在内存中执行真正的子串匹配。

拆字 AND 只是扩大候选集。「文件名包含原查询子串」必然意味着「文件名包含查询中的每个字」，
然后内存过滤会把结果收回原本语义，因此不会引入额外噪音。

## 不使用退避的情况

| 情况 | 原因 |
|---|---|
| 查询中没有中日韩文字 | 没有分词退避的必要 |
| 包含通配符 | 语义是整个文件名匹配，不能用子串复核 |
| `content:` 查询 | 命中来自文件内容，不能用文件名过滤 |

退避查询时，`NSMetadataQuery.resultCount` 表示放宽后的候选数。界面上应显示内存过滤后的真实结果数。

## 回归验证

`SelfTest.testCJKRelaxation` 验证：

- 中日韩字符识别与去重
- 退避谓词的 AND 结构
- 通配符、纯英文和内容查询不退避
- AND、OR、排除词和大小写不敏感的内存过滤语义
